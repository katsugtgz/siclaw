## What Docker Supports Today

Siclaw ships three Dockerfiles, one per deployment image:

- `portal` — Web UI + REST API + DB (the user-facing front door)
- `runtime` — Control plane: channels, cron, AgentBox spawner
- `agentbox` — Per-user execution runtime (spawned by Runtime)

For a single-machine setup, use [CLI & Local Server](/install/cli). The repository does **not** include a supported `docker compose` deployment.

## Build Images

From the repo root:

```bash
ssh-add -l # Verify the build host has a key with read access to aiops/codex.
make docker REGISTRY=registry.example.com/myteam TAG=latest
```

The AgentBox build forwards the SSH agent through BuildKit. Its GitLab host key
is pinned in `docker/gitlab-known-hosts`; SSH credentials are not copied into
the image. If `ssh-add -l` shows no identity, load an authorized key with
`ssh-add /path/to/key`. Direct `docker build` invocations need `--ssh default`
too. CI builders need equivalent read access to `aiops/codex`.

That builds:

- `registry.example.com/myteam/siclaw-runtime:latest`
- `registry.example.com/myteam/siclaw-portal:latest`
- `registry.example.com/myteam/siclaw-agentbox:latest`

To build one image only:

```bash
make docker-runtime  REGISTRY=registry.example.com/myteam TAG=latest
make docker-portal   REGISTRY=registry.example.com/myteam TAG=latest
make docker-agentbox REGISTRY=registry.example.com/myteam TAG=latest
```

## Push Images

```bash
make push REGISTRY=registry.example.com/myteam TAG=latest
```

Or push individually:

```bash
make push-runtime  REGISTRY=registry.example.com/myteam TAG=latest
make push-portal   REGISTRY=registry.example.com/myteam TAG=latest
make push-agentbox REGISTRY=registry.example.com/myteam TAG=latest
```

## Runtime Notes

- The Portal image serves the Web UI on container port `3003`.
- Runtime and AgentBox communicate over mTLS inside the cluster.
- The AgentBox image is designed to be spawned by the Runtime inside Kubernetes.
- Core skills are baked into the images; dynamic skills and credentials are synced at runtime.
- The AgentBox image builds the open-source Codex CLI from the protected
  `aiops/codex` `main` branch, verifying the exact `CODEX_COMMIT` in
  `Dockerfile.agentbox`. Official upstream commits are mirrored unchanged on
  `upstream/main`; Siclaw's minimal source changes live on `main`.
  Set `SICLAW_AGENT_ENGINE=codex` on Runtime (`runtime.env` in Helm) to select
  Codex for AgentBox sessions. Codex owns its native execution, file tools,
  planning, compaction and subtasks. Siclaw enforces grants, whitelist execution,
  credential brokering and sanitization at its native executor boundary.
  Codex currently requires Responses models and does not support cross-Agent
  handoff. Unsupported requests fail explicitly; they do not silently run Pi.
  The same chat API and event stream are used by both engines. See
  `docs/design/codex-native-runtime.md` for remaining acceptance gates.
- `SICLAW_CODEX_BIN` can point to a separately built Codex executable for local testing.
  After building Siclaw, run `SICLAW_CODEX_BIN=/path/to/codex-rs/target/release/codex
  node scripts/test/codex-native-brain-smoke.mjs` to check the real session factory
  against a fake Responses provider, including native child execution, file
  operations, security denials, resume and Stop. Run
  `scripts/test/codex-code-mode-smoke.mjs` inside the image to validate the
  catalog's Code Mode/Responses Lite path and matching source-built helper.
